### Clipboard history panel (⌃⌥V)

- The user asked for an Alfred-style clipboard history with text and image preview. First version: record text and images, search, preview, paste; pin and delete entries. Left for later: snippets, merge/paste-as-plain-text, per-app rules in the UI, Companion-side sync.
- `ClipboardService` (installed in `AppDelegate`) polls `NSPasteboard.changeCount` every 0.5 s while enabled and registers ⌃⌥V (`GlobalHotkeys.ID.clipboard`, `HotkeyAction.clipboard`, so it shows in the 快捷键 pane). Text wins over image when both are on the pasteboard.
- `ClipboardHistoryStore` keeps `~/Library/Application Support/SmartIMEHost/clipboard/index.json` plus `images/<id>.png` (0600/0700, no backup). Newest first, deduplicated by SHA-256 (copying again moves the entry up), capped at 300 entries and (since 2026-10-06) 7 days by default (1/7/30/90 in settings); pinned entries survive both. Text over 1 MB and images over 20 MB are skipped.
- Privacy: nothing is recorded from password managers (`ClipboardSettings.excludedApps`) or when the pasteboard carries `org.nspasteboard.ConcealedType`/`TransientType`/`AutoGeneratedType`. Terminals are recorded, unlike the input journal. Default is on; a toggle in the new 剪贴板 pane turns it off.
- `ClipboardPanel` is a non-activating floating panel (search field, list with app icons and ⌘1–9, preview on the right: text or image, plus time, app, and size). Keys: ↑↓, ⏎, ⌘1–9, ⌘P pin, ⌘⌫ delete, Esc; clicking elsewhere closes it. Choosing writes the entry to the pasteboard and sends ⌘V when Accessibility access is granted, else the toast says to press ⌘V.
- Fix after the first live use: ↑↓ stuttered because every selection change decoded the full image file and laid out up to 20,000 characters with text selection on. The panel now decodes a 1200 px thumbnail once per entry (`previewImage`, `NSCache`) and previews 4,000 characters without selection.
- Measured the panel in a standalone harness (real window, 29 entries, 1800×1000 PNGs, a 28,000-character text; per ↑ step including layout): long text 650 ms (SwiftUI `Text` layout, even cut to 4,000 characters), first visit to an image 33 ms, short text 1.5 ms. The preview is now an `NSTextView` (long text 9 ms) and images within three rows of the selection are decoded in the background (first visit 3 ms). The harness is not in the repository.
- Still stuttering on the real machine after that. `sample` of the running input method while holding ↓: the main thread was 92% idle and SwiftUI layout took about 7%, so the cost is not our computation. Added a log line when the panel closes (event age, handling time, gap between keys for ↑↓) and a `ClipboardPanelBlur` defaults switch that replaces the blur with a solid background, to tell rendering from key delivery.
- Third pass, measured on a standalone copy of the panel (same code, 9 entries plus a 28,000-character one, ↓ every 50 ms; main-thread time per step from the run loop waking to sleeping after the Core Animation commit): SwiftUI p50 12.8 / p90 23.7 ms. The preview pane was about 85% of it, but an AppKit preview inside the SwiftUI panel still cost ~10 ms. With a background thread keeping the CPU warm, the same step took 3.7 ms: short bursts of UI work run on a slow core, so every millisecond of work counts about three times.

Same copy: p50 7.6 / p90 13.4 ms, 1.6 ms with a warm CPU. TextKit 2 cost about 1 ms of that warm step on its own. Blur and shadow made no difference to main-thread time.

### AI assist review fixes (PR #16)

- A review of PR #16 found these problems; each fix below is its own commit.
  - **Shifted replacement:** ⌃⌥R on a line ending in spaces replaced the wrong range ("这个接口有问题 " became "这This API…"). The line's range now comes from where it is in the field (`AIRewriteController.line(before:)`, `FieldText.range(ofTail:)`).
  - **Stale replacement:** every replacement first checks that the range still holds the text that was read. If not, the result is copied and the chip or popup says why (`AIReplacement`). Leaving a field closes the ⌃⌥R popup, so `Return` in the next field cannot replace there.
  - **Chip tied to learning:** the chip fired from the learning recorder, so it needed 智能学习 (off by default) and the journal. The input controller now reads the field itself after a commit that ends a sentence, only in apps with AI hints on.
  - **Modified keys accepted:** ⇧→, ⌥→ and ⌘→ accepted the chip. Only a bare `Tab` or `→` accepts now; once the chip shows only a message, both keys go to the app.
  - **First line dropped:** `cleanFreeText` dropped a one-line answer starting "Here is" or "Translation" (an Ollama "AI 没有返回结果"), and the colon-ended first line of a multi-line polish. A first line is now dropped only when the answer has more lines than the source.
  - **Old clipboard used:** ⌃⌥R in an empty field or on a blank line showed the old clipboard in the read-only popup. A field that reports its text now gets the "nothing to rewrite" message, and the input method's hand-over to the read-only flow uses only a selection copied with ⌘C. Without Accessibility access, a web page now needs select, ⌘C, ⌃⌥E.
- Tests: 6 new cases. 188 host tests pass locally through the harness. The chip trigger and the ⌃⌥R text pick-up run through `IMKTextInput` and are not unit-tested; they need a live check.
- Left open: when Ollama answers slowly, its availability check waits on the main thread (up to 0.6 s, cached for 30 s). ⌃⌥E is always registered and cannot be turned off.

- Root cause: Under InputMethodKit, `NSEvent` for Space (keyCode 49) can arrive with empty `characters` / `charactersIgnoringModifiers`. `RimeKeyTranslator` then returned `nil`, so `process_key` was never called; `handle(_:client:)` still returned `true` because `lastKnownState` still had composition text, so the key was swallowed and Rime never saw Space (first candidate / confirm).
- Fix: Map virtual key 49 explicitly to X11 keysym `0x20` (`XK_space`) in `RimeKeyTranslator.specialKeycode` so Space always reaches `librime`. Return was already mapped via keyCodes 36 and 76.
